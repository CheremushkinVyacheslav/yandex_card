Тестовое задание: интеграция с Яндекс.Картами
Стек: Laravel (бэкенд / API) + Vue 3 (SPA).
Контекст
Мы развиваем сервис работы с отзывами и данными бизнеса на картах — сбор отзывов, автоответы, виджет отзывов, поддержание карточек организаций в актуальном состоянии. Одна из ключевых задач сервиса — собирать данные с площадок (Яндекс Карты, 2ГИС), у которых нет официального API: всё приходится получать парсингом. Это задание — упрощённая модель реальной фичи: подключить карточку организации на Яндекс.Картах и показать её отзывы и рейтинг.
Что нужно сделать
Небольшое приложение из двух экранов:
1. Авторизация (логин / пароль)
Регистрация не нужна — достаточно одного сид-пользователя. Бэкенд на Laravel, SPA-аутентификация через Sanctum.
2. Страница настроек
Поле для вставки ссылки на карточку организации в Яндекс.Картах, валидация ссылки, сохранение в БД. После сохранения — подтягивание данных по этой организации.
3. Вывод данных организации
все отзывы по карточке (на практике Яндекс отдаёт примерно последние 600 — нужно вытянуть их полностью);
постраничная навигация по 50 отзывов на страницу;
средний рейтинг компании;
точные числа: количество оценок и количество отзывов отдельно;
каждый отзыв: автор, дата, текст, оценка.
Про парсинг (главное)
Официального API у Яндекса нет — данные получаете парсингом, и это центральная часть задания. Парсер должен:
принимать ссылку на любую организацию в Яндекс.Картах;
доставать все доступные отзывы (ориентир — до ~600), а не только первую выдачу;
корректно тянуть: средний рейтинг, число оценок, число отзывов.
У Яндекса есть защита от ботов и подгрузка отзывов скриптом по мере прокрутки — справиться с этим и есть суть задачи. Как именно (headless-браузер, разбор внутренних запросов карточки, что-то ещё) — на ваше усмотрение, в README поясните выбор.

Постраничная навигация
50 отзывов на страницу, переключение страниц без перезагрузки. Подумайте, что грузить за один раз, а что подкачивать: тянуть все ~600 разом по каждому запросу или кэшировать результат парсинга на стороне бэка — решение и его обоснование тоже оцениваем.
Технические требования
Логика парсинга и работы с внешним источником вынесена из контроллеров (сервис / класс-обёртка), не «в лоб» в маршруте.
Валидация входных данных, осмысленная обработка ошибок (страница недоступна, изменилась разметка, пустой ответ).
Vue 3, Composition API; состояние загрузки и ошибки видно в интерфейсе.
Понятная структура БД (миграции).
Дополнительные требования
Эти пункты приближают тестовое задание к реальным условиям работы с площадками без API. Если не успеваете реализовать всё — часть можно описать словами в README, но покажите понимание задачи.
1. Устойчивость к смене разметки. 
Яндекс регулярно меняет вёрстку и внутренние запросы — парсер должен не «молча» возвращать пустоту или мусор, а обнаруживать, что источник изменился, и сообщать об этом (лог / понятная ошибка / статус). Опишите в README, как ваш парсер поймёт, что он сломался.
2. Обоснование подхода к парсингу. 
В README сравните выбранный способ (разбор внутренних JSON-запросов карточки vs headless-браузер): почему выбрали именно его, какие плюсы, минусы и риски (стабильность, скорость, хрупкость к смене токенов/разметки).
3. Масштаб и фоновая обработка. 
Представьте, что подключена сеть из ~50 филиалов, у каждого до ~600 отзывов. Такой объём нельзя парсить синхронно внутри HTTP-запроса. Реализуйте (или подробно опишите) парсинг через очередь (queue / job) с индикацией прогресса и повторными попытками при сбое.
4. Анти-бан на объёме. 
Опишите в README, как избежать блокировки при регулярном парсинге многих карточек: троттлинг запросов, паузы/бэкофф, ротация прокси и User-Agent, обработка ситуации «нас забанили».
5. Идемпотентность и история изменений. 
При повторном парсинге той же организации не создавайте дубли, а обновляйте записи. Продумайте хранение снимков данных, чтобы можно было увидеть, что изменилось между парсингами (было → стало). Достаточно описать модель данных, даже если полностью не реализуете.

Что оцениваем
Архитектуру и читаемость кода, обработку ошибок и крайних случаев, адекватность решения по парсингу и его устойчивость, аккуратность работы с API между фронтом и бэком. Идеальный пиксель в вёрстке не важен.
